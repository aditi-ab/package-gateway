# Administration UI

Open `/admin/` on the gateway origin. The administration UI communicates only with the management API on the same gateway origin.

## First use with local authentication

Local authentication is enabled when `Authentication__Mode` is `Local` or `LocalAndEntra`. After the database migration and application startup, open `https://gateway.example/admin/`. The first-use form asks for a username and password. Usernames must contain 3 to 100 letters, numbers, periods, underscores, hyphens, or `@`. Passwords must contain 12 to 128 characters and must not contain the username.

Submitting the form creates the initial local administrator and signs it in. The sign-in page adapts to narrow screens without horizontal scrolling, and its centered product header identifies the security console consistently with signed-in pages. Open **Local users** to create, enable, disable, reset, delete, and assign roles to additional accounts. Generated temporary passwords are displayed once and must be changed at the next sign-in. If the current or new password is invalid, the password dialog displays the validation message and remains open for correction. A temporary-password session can load `/admin/`, where the required password dialog remains open. Use **Sign out** in the dialog to return to the login screen and choose another user. If the server rejects an existing session as unauthorized or forbidden, the administration UI clears it and returns to the login screen automatically. The final enabled administrator cannot be disabled, deleted, or demoted.

Local sessions use secure, HTTP-only cookies and require HTTPS in deployed environments. Development mode permits HTTP on the local development server and uses development-only cookie names without the production `__Host` prefix. Keep `Authentication__DataProtectionKeysPath` on durable storage so application restarts do not invalidate every active session. A local administrator receives the full `Administrator` role.

## Users and identity providers

Open **Access > Users** to manage local accounts and LDAP, OpenID Connect (OIDC), and Microsoft Entra providers on one page. LDAP providers participate in username and password sign-in. OIDC providers use an HTTPS authority or discovery URL and the authorization-code flow. Administrators can enable automatic provisioning, assign default product roles, and map directory or token role values to `Reader`, `SecurityReviewer`, `RepositoryAdmin`, or `Administrator`. Local authentication remains available as a recovery path.

LDAP bind passwords and OIDC client secrets are encrypted with the application's data-protection keys. Persist those keys across restarts. For OIDC, register `/admin/auth/external/{provider-id}/callback` on the management origin as the redirect URI. Test a provider before enabling it.

The user and provider workflow is shared with the other Aditi administration consoles. It uses the same responsive tables, one-time password dialog, role selector, provider form, validation, and confirmation behavior. The existing Entra connection is disabled instead of deleted.

Microsoft Entra users and groups remain in the organization's directory. Assign them the `Reader`, `SecurityReviewer`, `RepositoryAdmin`, or `Administrator` application role in Microsoft Entra. Secure Package Gateway validates those role assignments at sign-in and does not copy directory accounts into its local-user table.

The compact navigation header keeps Overview, Repositories, Packages, Review queue, and Policies as direct product-workflow links. Access groups Users and Access tokens. System groups Audit history. This matches the navigation structure used by API Gateway so common administration areas are recognizable between products. Repositories remains highlighted while viewing a repository or any of its submenus. Every signed-in page provides a Back action that follows the user's browser navigation history. The theme menu supports System, Light, and Dark modes and remembers the selection in the browser. System mode follows operating-system changes. The administration interface initially selects Swedish for a Swedish browser or operating-system locale and English for other locales. The language button shows the active locale code. Its menu offers System with the detected locale, English, and Swedish. An explicit language selection is remembered in the browser. Displayed dates and times use the local-time format `yyyy-MM-dd HH:mm:ss`.

The product header and browser tab use the official Secure Package Gateway icon. The header preserves the icon's proportions without cropping it. The footer links directly to the Package Gateway source repository on GitHub.

Page headings, forms, filters, tables, status indicators, expansion panels, menus, dialogs, and scrollbars use the same theme-aware administration design system as the other Aditi gateway consoles. Interactive controls provide visible hover and keyboard-focus feedback, forms use consistent outlined fields, and layouts adapt from wide tables and grids to narrower screens without hiding primary actions or state. Compact utility actions use recognizable icons with accessible labels and tooltips, while workflow actions such as **Manage**, **Review**, **Assign**, and **Remove** remain labeled. Page navigation uses a brief transition consistent with the other gateway consoles and disables that motion when the browser requests reduced motion.

Menus, single-choice fields, tooltips, disclosure panels, and modal workflows use accessible native administration controls with keyboard navigation and viewport-aware positioning. Dialog titles and actions remain visible while long dialog content scrolls independently. Multi-value policy and repository choices are presented as constrained selections or removable values instead of comma-separated free text.

The overview summarizes repository and package-version counts, approved versions, and versions requiring attention across manual review, quarantine, and blocked states. Its service-health section reports database readiness, background execution, vulnerability-provider state, gateway version, and process start time. The manual-review table shows the highest-risk pending items with package name and version, repository, format, decision explanation, risk, security signals, scan time, and links to the relevant repository review workflow. Repositories creates gateway endpoint containers. Repositories and Review queue provide Refresh actions that reload their current server-side data without reloading the browser page. Open a repository to manage its package versions and review queue, configure upstreams, assign policies, and manage settings. The repository Packages, Review queue, Upstreams, Policies, and Settings sections use the standard compact tabs and switch their content in place without navigating or reloading the administration page. The Packages and Review queue tabs provide the same search, inspection, refresh, and security actions as their global counterparts, with every query restricted to the selected repository. A repository can contain both NuGet and npm upstreams, and its slug is shared by both protocol endpoints.

When creating a repository, the endpoint slug is derived from its display name and remains editable. New repositories receive balanced security policies. The upstream setup offers NuGet.org and npmjs presets as well as manual HTTPS endpoints. Priorities are evaluated independently for NuGet and npm.

Policies provides guided configuration for vulnerability severity, cooldown, licenses, integrity, signatures, npm install scripts, and package allow or deny patterns. Policies can be reused across repositories and targeted to NuGet, npm, or both formats. A repository's Policies tab separates assigned and available policies, shows each policy's name, type, formats, and enabled state, and provides explicit Assign and Remove actions. Removing an assignment requires confirmation and affects future acquisitions and rescans. Policy definitions remain centrally managed from the global Policies page. Advanced JSON is available for administrators who need to inspect or edit the stored versioned configuration. Expansion panels throughout the administration UI use the same bordered, rounded visual treatment, including Advanced JSON in the policy editor.

Packages searches acquired and scanned NuGet and npm versions across repositories. Operators can filter by package name, repository, format, and status, or select an All option to omit that filter. Select **Add package** to choose a repository and format, then search its enabled upstreams. The column headings remain visible while scrolling a long result list. Expand a result to inspect its description. Open its **Add and scan** menu and select the exact available version to acquire. Upstream search and version listing do not download package bytes. Selecting a version resolves it through normal upstream priority and uses the same integrity, scanning, vulnerability, and policy pipeline as a client-triggered acquisition.

The package name is read from the acquired NuGet `.nuspec` or npm `package.json`, while a separate normalized identity is retained for case-insensitive protocol matching. npm package names are normally lowercase because the npm registry requires new package names to be lowercase. Packages acquired before manifest-name capture was enabled retain their normalized display name until they are rescanned.

The Risk column is the aggregate score contributed by archive, integrity, malware, install-script, and vulnerability findings. Select its information icon for a theme-aware explanation. The table uses dense rows and compact uppercase status chips without repeating the decision explanation in every row. Select Manage to inspect the full explanation in bordered expandable sections with compact lists, including configured policy names, readable rule outcomes, individual security findings and their score contributions, and the package-version audit history. This distinguishes a score-based outcome from a stricter policy result or a manual operator decision. Review queue uses the same table-header treatment as the other list views.

A security reviewer can send an approved version to the Review queue, approve a version that requires review or is quarantined, quarantine or block eligible versions, and queue a rescan. A repository administrator can proactively add packages. An administrator can remove an exact package version from Manage after confirming the destructive action. Removal clears the cached artifact and evaluation state, while retaining an immutable audit event, so the next request can acquire and evaluate it from scratch. Destructive actions, including package removal, policy deletion, upstream removal, repository disabling, and access-token revocation, use application confirmation dialogs with explicit Cancel and confirmation actions. The wide Manage and Review dialogs also provide an explicit Cancel action and remain responsive on narrow screens. The Review dialog presents the same policy reasons, security findings, and decision history as Manage on the Packages page.

Access tokens provides repository selectors instead of raw scope entry. A token can read all current and future repositories or a selected set. Expiration can use a preset, a custom local date and time, or Never. Review queue records approve, block, and quarantine decisions or queues a rescan. Audit history exposes the immutable operational trail in a table. Its entity-type dropdown is populated from the complete audit store, applies the selection immediately, and can be cleared to show all events. Refresh reloads both the available entity types and the displayed events.

Role enforcement remains server-side. `Reader` can inspect, `SecurityReviewer` can decide or rescan, `RepositoryAdmin` manages repositories, upstreams, and policies, and `Administrator` additionally manages protocol tokens. A token secret is displayed once. Store it in an approved secret manager before closing the dialog.
